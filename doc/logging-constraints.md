# 日志优化约束

> AI 协作入口：修改日志、截图通知、WebUI 日志消费、视觉/识别/匹配或设备链路前，先完整阅读本文件。
>
> 本文件是持续维护的规范，不是一次性实施记录。新增业务或上游同步引入日志时，必须补充文末的增量审计。

## 1. 权威顺序与适用范围

发生冲突时按以下顺序判断：

1. 当前已确认的用户意图和 issue 验收条件；
2. 子系统业务约束文档，例如专精业务以 `doc/mastery-constraints.md` 为准；
3. 本文件定义的日志、截图通知与消费者合同；
4. #48 冻结 ledger，作为历史范围与目标形状的不可变证据。

本文件覆盖 Python `logger.*` 调用、WebUI 日志/截图消费者、视觉与设备链路、识别与匹配链路，以及后续合入的新业务日志。日志优化只能改变可观测性，不得改变业务返回值、异常传播、重试次数、状态机、调度、通知去重或设备动作。

## 2. 冻结基线不可变

#48 的冻结 ledger 共 749 行，全部必须实施：

- 278 行 `scope_required` 是逻辑记录和实际文件字节的双 95% 体积主范围；
- 471 行 `scope_consistency` 是截止线后的语义一致性范围；
- 两种 selection basis 都是实施范围。双 95% 只决定施工优先级，不是保留旧语义的许可；
- 同一源码日志语句产生的所有消息形状采用同一合同，不得并存新旧两套语义。

`.scratch/log-baseline/` 中的原始日志、报告、声明和 ledger 已获 owner-approved waiver。不得改写报告、修改 ledger、降低冻结阈值或放松严格校验器。`doc/log-baseline.md` 只描述采集与冻结流程。

上游在冻结后新增的日志不回填 ledger。它们进入本文件末尾的“增量审计”，以同一合同判断和测试。

## 3. 日志语义合同

### 3.1 级别和所有权

- 低层例行成功静默。截图成功、模板命中/未命中、OCR 正常返回、点击/滑动成功、设备命令成功、候选遍历和单次轮询不逐条记录。
- 高层只记录有限的代表事实。一次 operation 由最了解最终结果的边界记录一次；下层不得先记录同一失败再抛给上层重复记录。
- `INFO`：真实业务状态迁移、用户可感知动作完成，或一次高层 operation 的最终成功。
- `WARNING`：一次 operation 经内部重试后恢复，或发生可继续但需要关注的降级。内部每次失败静默，恢复后由 owning boundary 最多记录一次。
- `ERROR`：重试耗尽或 operation 最终失败，由最终处理边界记录一次。意外异常保留一条完整因果链，不在多层重复 traceback。
- `DEBUG` 也必须有语义价值和有限字段；它不是对象 dump、循环刷屏或临时 print 的避难所。

同一状态的重复观察静默；只有真实状态变化才记录。重试、轮询和进度属于一个 operation，不因循环次数变成多个业务事件。

### 3.2 有界字段

日志优先使用稳定的 `key=value` 事实。字段必须可枚举或显式有界，并满足：

- 不记录任意对象、DB 行、完整计划字典、OCR 原始对象、无限列表或候选全集；
- 不记录 token、账号、UID、cookie、请求头、设备凭据或其它秘密；
- 字符串使用业务上天然有界的标识或名称；列表只记录经合同挑选的少量代表项；
- 不得用 `repr`、`str(object)` 或简单截断来伪装无界 dump；
- 需要关联时使用稳定 ID，例如 `plan_id`、`task_type`、`scene`，不展开整个实体。

状态迁移建议形状：

```text
operation={operation} entity_id={entity_id} from_state={from_state} to_state={to_state} trigger={trigger} action={action} result={result}
```

字段按具体业务删减，不为填模板制造无意义字段。

### 3.3 代表事实

一次识别或匹配 operation 需要诊断上下文时，只保留去重后的有限代表项：

- 距离最近的 3 项；
- 最慢的 1 项；
- 首个无效或缺失项；
- 最终选中的 1 项。

各角色可能指向同一项，去重后最多 6 项。不得因为候选很多而逐候选记录，也不得靠截断候选 ID 列表保留旧噪音。

### 3.4 长任务进度

短任务不发进度日志。确需报告的长 operation：开始后满 5 分钟才允许首条进度，此后最多每 15 分钟一条；完成或失败由 owning boundary 记录最终结果。不得新增固定高频心跳。

## 4. 视觉、识别、匹配、截图与设备链路

- 低层截图、裁剪、颜色计算、模板查找、OCR、匹配候选和设备命令的正常成功路径静默。
- 高层记录最终识别结果、真实 Scene 迁移、最终选择、恢复后的降级或重试耗尽；不得逐层重复同一事实。
- 保留原业务返回能力：日志删除或重构不得吞掉返回值、异常、截图对象、候选结果或设备响应。
- 诊断信息使用 §3.3 的代表事实，不能恢复对象 dump。
- 截图文件写入完成是通知消费者的前置条件；不能让前端读取半写文件。

## 5. Scene 快照与 WebUI 合同

WebUI 的 Scene 快照是事件驱动合同：

1. 页面打开时读取一次最新截图；
2. WebSocket 每次重新连接成功时读取一次最新截图；
3. 预览从关闭变为启用时读取一次最新截图；
4. 运行中只有真实 Scene 变化且对应截图已经写完后，才通知前端刷新一次；
5. 同一 Scene 的后续截图不重复刷新。

禁止新增定时轮询、五秒兜底、逐截图推送或通用截图事件。日志接口的“最近 100 行”必须按实际逻辑行裁剪，并保持移动端连续阅读合同。

服务端事件名、载荷和前端消费者必须成对修改。新增或改名任何事件前，先搜索所有生产者和消费者，并以合同测试锁定双方。

## 6. 专精子系统映射

修改 `mastery.py`、`mastery_reader.py`、`mastery_db.py`、专精相关排班路径或其日志前，必须完整阅读 `doc/mastery-constraints.md`。其中截图权威、状态机、恢复矩阵、通知去重、排班 gate 和 `enable_mastery` 语义均高于日志整形。

- 房间/OCR 的重复读取、矩阵重试、倒计时刷新同值和不变状态静默；不得因“保守等待”制造每轮日志。
- 真实计划状态迁移可记一条 `INFO`，使用 `plan_id`、`from_state`、`to_state`、`trigger`、`action`、`result` 等有限事实，不展开计划或房间对象。
- 内部每次 OCR/换人/读取重试静默；重试后恢复由拥有该 operation 的边界最多记一条 `WARNING`，耗尽由最终处理边界最多记一条 `ERROR`。
- 通知日志只在通知确实发送时记录，并服从 `mastery_notify` 去重；不得把被去重的尝试写成已发送。
- “截图为准”意味着日志必须描述实际读取与最终决策，不能把 DB 缓存提示写成已确认的游戏状态。
- 专精邮件正文与对应 `INFO` 日志需要共享文案时，保持 `doc/mastery-constraints.md` 规定的发送时机、档位、技能真名和完成时间口径。

## 7. Rebase、合并与冲突处理

- `fork/alpha` 已存在的产品功能和业务行为是新基准；日志分支保留基线采集、严格 ledger 校验、文档、测试和本文件合同。
- 不得整块选择 ours/theirs。逐个调用点确认业务所有者、最终 handling boundary、消费者和测试。
- 文本自动合并不代表语义兼容；上游新增的 `logger.*`、截图事件或消费者都要进入增量审计。
- 若业务文档与旧日志形状冲突，保留业务不变量，再调整日志形状和测试。
- 不改写或强推 `alpha`。日志分支需要重写时，只更新 fork 的 `feat/log-optimize`，并使用带明确期望值的 `--force-with-lease`。

## 8. 测试与验收

日志改造使用测试先锁定合同，至少覆盖受影响的以下行为：

- 低层成功静默，高层最终结果一次；
- 不变状态静默，真实迁移一次；
- 重试中间过程静默，恢复一次 warning，耗尽一次 error；
- 有界字段和代表事实去重上限；
- 页面打开、WebSocket 重连、预览重新启用各读一次最新截图；
- Scene 变化一次、同 Scene 静默、文件写完才通知/读取；
- 最近 100 行和移动端合同；
- 生产者与消费者事件一致。

改动后按范围运行专项测试、全量 Python 测试、Ruff lint/format、前端测试和构建。测试断言日志语义与次数，不把时间、路径或随机数据写成脆弱快照。

## 9. 计数与报告口径

每个实施切片报告改造前后的逻辑记录数和实际文件字节，并明确样本类型：

- #48 原始两小时窗口是历史基线；
- 固定 fixture/replay 可以做严格配对的确定性对比；
- 新代码实机窗口只有在环境、负载、时长和配对条件一致时才可称严格对照。

上游业务改变了代表性任务流程、日志语义或日志消费者后，旧 before 窗口不再是严格配对样本。此时仍可用于历史规模与热点定位，但必须明确披露，不得伪造严格两小时 before/after。

## 10. 上游增量审计

每次同步上游后新增一节，至少记录基线提交、涉及子系统、日志分组、决策、测试和状态。冻结 ledger 不随之变化。
